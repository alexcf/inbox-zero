# Received mailbox events

This optional Google Inbox producer is disabled unless `MAILBOX_RECEIVED_ENABLED` is exactly `true`. Set `MAILBOX_RECEIVED_ACCOUNT_ID` to the one personal Google EmailAccount ID authorized by the receiver, `MAILBOX_RECEIVED_URL` to its HTTPS mailbox-event endpoint and `MAILBOX_RECEIVED_SECRET` to the matching secret. Keep configuration server-side. No work account should be mapped to the personal receiver.

Apply the database migration before enabling. Schedule `GET /api/cron/mailbox-events` with `Authorization: Bearer <CRON_SECRET>` at least once a minute; the included Vercel schedule does this on Vercel, while other installations must configure their own scheduler. Existing pending rows remain undelivered while disabled. Treat `held` outbox rows as operator review, not success; do not log their identifiers or payloads. Retain receiver deduplication records for as long as retries or retained outbox records might be replayed.

The selected account's Google webhook processes synchronously and returns a retryable error when history or outbox processing fails, including provider rate limiting. Pub/Sub redelivery is bounded by its configured retention; it is not an independent catch-up scheduler. The history window and its received-message outbox entries commit together. Enqueue failure, missing message identity/labels, a truncated history window, expired history, or an absent cursor prevents this producer from advancing its cursor. Gmail must already have a valid stored cursor before enablement. This feature cannot recover messages omitted before enablement, messages already outside Gmail history, or inbox messages missed by an upstream notification/watch failure. If history omits labels, the producer fetches minimal current metadata; it holds ambiguous archived messages because current labels cannot prove their labels at arrival. Monitor coverage independently and review gaps before any backfill. This implementation handles Gmail INBOX message additions only; it does not claim Outlook or archive-only coverage.

Each cron invocation processes at most three rows, with a five-second timeout per HTTP attempt; database stalls can still extend runtime. A process interrupted while holding a lease leaves it recoverable after two minutes. Retries use a stable event ID and body and a fresh timestamp/signature. A timeout has an unknown outcome and is retried, relying on the receiver's event-ID deduplication. HTTP 202 completes delivery; non-transient 4xx responses are held. Do not enable until the deployed version, account mapping, TLS endpoint, migration, scheduler, and receiver interoperability have been verified.

The selected-account webhook currently runs the existing rules/AI history processing before it commits the outbox and returns its Pub/Sub acknowledgement. A slow request can exceed the Pub/Sub acknowledgement deadline, causing redelivery and repeated execution attempts; existing rule locks and deduplication are not a proof that every side effect is idempotent. A process interruption before the commit can also require redelivery. Do not enable until the host's Pub/Sub deadline, timeout behavior and rule-side-effect idempotency are reviewed and exercised with synthetic input. Moving rule processing after the cursor commit without a separate durable rule-work queue would risk losing rule execution on a crash, so this patch does not do that. This route does not establish end-to-end webhook reliability.
