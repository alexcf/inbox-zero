# Received mailbox events

This optional Google Inbox producer is disabled unless `MAILBOX_RECEIVED_ENABLED` is exactly `true`. Set `MAILBOX_RECEIVED_ACCOUNT_ID` to the one personal Google EmailAccount ID authorized by the receiver, `MAILBOX_RECEIVED_URL` to its HTTPS mailbox-event endpoint and `MAILBOX_RECEIVED_SECRET` to the matching secret. Keep configuration server-side. No work account should be mapped to the personal receiver.

Apply both database migrations before enabling. Schedule `GET /api/cron/mailbox-events` with `Authorization: Bearer <CRON_SECRET>` at least once a minute; the included Vercel schedule does this on Vercel, while other installations must configure their own scheduler. Existing pending rows remain undelivered while disabled. Treat `held` outbox rows as operator review, not success; do not log their identifiers or payloads. Retain receiver deduplication records for as long as retries or retained outbox records might be replayed.

The selected account's Google webhook records the highest notified history ID in `MailboxReceivedCheckpoint` before returning 200. A database failure or missing cursor returns 503; provider rate limits do not prevent the durable receipt. The cron worker leases the checkpoint, fetches Gmail history, commits Received events and its independent cursor atomically, then runs Inbox Zero's existing rules against their original cursor. A failed fetch, rule, or outbox commit leaves the checkpoint pending for retry. A newer notification received during a lease raises the target and keeps the checkpoint pending after the older target completes. Both cursors must reach the target before the checkpoint becomes idle. Pub/Sub redelivery is bounded by its configured retention; the checkpoint is the independent retry scheduler after acknowledgement.

Enqueue failure, missing message identity/labels, truncated history, expired history, or an absent cursor prevents Received progress. Gmail must already have a valid stored cursor before enablement. Enable only after no older selected-account webhook processing remains in flight, so the first checkpoint captures the intended baseline. This feature cannot recover messages omitted before enablement, messages already outside Gmail history, or inbox messages missed by an upstream notification/watch failure. If history omits labels, the producer fetches minimal current metadata; it holds ambiguous archived messages because current labels cannot prove their labels at arrival. Monitor coverage independently and review gaps before any backfill. This implementation handles Gmail INBOX message additions only; it does not claim Outlook or archive-only coverage.

Each cron invocation processes at most three rows, with a five-second timeout per HTTP attempt; database stalls can still extend runtime. A process interrupted while holding a lease leaves it recoverable after two minutes. Retries use a stable event ID and body and a fresh timestamp/signature. A timeout has an unknown outcome and is retried, relying on the receiver's event-ID deduplication. HTTP 202 completes delivery; non-transient 4xx responses are held. Do not enable until the deployed version, account mapping, TLS endpoint, migration, scheduler, and receiver interoperability have been verified.

Rules can still be attempted twice if the worker stops after a side effect and before the legacy cursor advances. Existing rule locks and deduplication are not proof that every side effect is idempotent. The cron's ten-minute checkpoint lease should exceed its five-minute runtime, but a hung worker can overlap a later lease. Review rule-side-effect idempotency and test interruption/retry with synthetic input before enabling. The worker's Gmail history fetch is still unbounded by page count; large gaps can exceed its runtime. This route does not establish end-to-end webhook reliability without provider, scheduler, receiver and live coverage evidence.
